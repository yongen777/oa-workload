# 设计说明：为什么是这几个规则

这份文档解释 `oa.py` 里几个看起来"奇怪"的决定。改代码前先读它，否则很容易把约束改软。

---

## 1. 计数口径 = 交付物件数，不是提交次数

多数企业 OA 的工时模块是「**一个项目一周只能提交一次**」，季度内可补录。这意味着：

- 按「提交次数」算，一个月物理上限 4~5 次，配额要求「30 次/月」直接不成立；
- 真正被统计的是**上传的交付物数量**（表单里每行「交付内容 + 数量 + 附件」，系统自动累加）。

所以 `qty_of(entry) = Σ 交付物.数量`，所有统计（日/周/月/参考线）都只认这个数。

## 2. 周期 = 上周六 → 本周五，且目录不用周序号

系统里的「本周」常常不是自然周。常见口径是**上周六到本周五**（周五截止提交）。

由此两个决定：

1. `paths.week_label = "W_{s:%m%d}-{e:%m%d}"` —— 用**日期区间**做目录名。
   不用 `W43` 的理由：ISO 周号与业务周必然错位（例：2026-10-17 的 `isocalendar()` 是第 **42** 周，而业务上它是某个"第 43 周"的第一天）。日期区间永远对得上，换年也不会错。
2. 目录层级：`月 / 项目 / 周 / 日`。
   月在最外层是因为"按月核算"；项目在周之上是因为**提交单位是「项目 × 周」**（提交按钮在项目行上）。

> 如果你的系统是自然周（周一到周日），只改 `week_label` 和 `oa_week()` 里的偏移即可，其余不动。

## 3. 参考线算法（2026-10-30 起不再叫「闸门」）

```
当月参考线 = min(week_min × 本月已收口周数, month_min)
已收口周   = 该周的周五 <= 今天
```

- 月初第一周还没过完时，参考线为 0。
- 已过去的月份按整月 `month_min` 结算。
- 未来月份不计。

**它只是一个提示数字。** `quota.mode` 默认 `report`：`export-week` 照常出单，只在文本里写「月累计 X 件，低于参考线 Y 件」。
只有显式改 `"mode": "strict"`，才会拒绝出单并写《缺口预警单》。

### 为什么从「硬闸门」退成「参考线」（2026-10-30 变更）

旧设计用配额闸门逼着每个月必须凑到 30 件。实际用下来的副作用是**反的**：

1. 闸门只约束「出单那一刻的总数」，并不能保证每天记的是真实产出；
2. 于是出现了「先定达标数、再往十天里分配条目」的做法——顺序反了，本质就是凑数；
3. 又为了"看起来合理"给每天设 2~3 件的经验区间，结果**真实产出多的一天被压缩、少的一天被补件**，两边都失真。

现在的规则：**每日件数严格等于当天真实产出，不设下限也不设上限**；月累计只是真实工作自然累加的结果。
如果月底真的不够 30，那是工作量/记录的真实缺口，应该暴露出来，而不是用拆分或补记把它抹平。

> ⚠️ 不要因为「要凑够参考线」就回头给某一天加件。这类改动没有任何代码拦得住，只能靠这条约定。

## 3.1 为什么要记 `source`

同一天的产出经常来自多个工具：本 agent 写文档、teleagent 跑批、AI Studio 出结果、用户手工改代码。
如果只记「今天 6 件」，事后无法回答**这 6 件是不是全的**。

所以每条登记带 `source`，渲染时按来源分组汇总；用户给的条数与合计条数必须一致，漏一条当场就能看出来。

## 4. 为什么白名单是硬拒绝而不是警告

警告会被忽略。真实事故：为了凑件数，把「工时台账整理」「填报数据核对」这类**为管理工具本身做的工作**当成交付物登记，被主管一眼看穿。

所以：

- 交付内容不在白名单 → `log` 直接 `die`，台账根本不落这条；
- 判断"算不算本项目产出"的标准写成一句话：**这条产出如果发给主管，他会不会认为是本项目的成果**。

校验必须放在**写入口**，不是出单口。出单时才检查，脏数据已经在台账里了。

## 5. 数据模型

`ledger.jsonl` 一行 = 一次登记（同一天可多行，渲染时按日期合并）：

```json
{"ts":"...","date":"2026-10-20","week":"W_1017-1023","project":"<code>",
 "work_types":["..."],
 "entries":[{"item":"<事项清单>","hours":3.5,"desc":"..."}],
 "deliverables":[{"content":"<交付内容>","qty":1,"file":"..."}],
 "qty":1,"source":"workbuddy"}   // workbuddy|teleagent|ai_studio|other_tool|manual
```

派生关系：

```
ledger.jsonl  ──渲染──▶  当日填报.md（人读）
              ──聚合──▶  _Weekly_Submit_Package/填报对照文本.txt + 交付物清单.csv
```

`当日填报.md` 与周包都是**幂等派生**：删掉重跑即可，不要手改。

## 6. 已知边界

| 边界 | 说明 |
|---|---|
| 无自动提交 | 多数 OA 无对外 API；本工具只产出可复制的文本 |
| 不判断"这算不算交付物" | 由使用者判断，工具只校验白名单与项目相关性 |
| 不知道某天真实工作量 | 工具不生成工作量，只记录你给的；「没有日下限」意味着它也不会提醒你"今天记得太少" |
| 删除是追加式的反面 | 删条目要手工改 `ledger.jsonl`（按日期 grep 掉整行），没有 undo 命令 |
| `harvest` 只出候选 | 关键词猜测不可靠，必须人工确认后再 `log` |
